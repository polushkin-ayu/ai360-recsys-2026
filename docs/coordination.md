# Координация работы: команды, утверждения и Issues

Подробные ТЗ: [команда 1 — данные](teams/team1-data.md), [команда 2 — модели](teams/team2-models.md), [команда 3 — эксперименты](teams/team3-experiments.md). Сроки и общий показ — в [плане дня](day2.md).

Эта заметка действует на протяжении проекта. [Общий план](work_plan.md) задаёт цели и этапы, [протокол](research_plan.md) — правила экспериментов, планы [сегодня](day2.md) и [вторника](tuesday.md) — расписание и приоритеты. Здесь хранится единое распределение ответственности и список проверяемых утверждений; текущий статус и доказательства ведём в Issues/PR.

## Кто отвечает за проверки

| Команда / рабочая роль | Основная задача | Ответственность |
|---|---|---|
| Данные и оценка | [#1](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/1) | К5–К6: разбиение, неизвестные ID, корректность RMSE |
| Модели и обучение | [#2](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2) | Т1–Т4 и К1–К4: формулы, эквивалентности, forward, градиенты и шаг оптимизатора |
| Эксперименты и анализ | [#3](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) | Г1, затем Г2: сравнения, интерпретация и оформление доказательств для защиты |
| DCN, если сохраняем | [#4](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/4) | Г3 и проверки реализации DCN; направление необязательно |

Состав и логины назначаем на занятии. Это роли, а не обязательные отдельные команды фиксированного размера: при сокращении числа участников роли объединяются согласно [общему плану](work_plan.md).

**Основной Issue определяет владельца результата. Несколько ссылок у утверждения означают зависимости и сотрудничество, а не дублирование работы.** Например, для Г1 команда #1 предоставляет данные, #2 — модели, #3 проводит сравнение и отвечает за вывод. Для К5–К6 владелец — #1, а #3 проверяет пригодность данных и метрики для эксперимента. Для Т1–Т4 владелец — #2, #3 помогает включить объяснение в защиту.

Для каждого утверждения назначаем одного ответственного и проверяющего из другой команды. Ответственный организует проверку и прикладывает доказательство; проверяющий воспроизводит её или проверяет математический вывод. Имена и статус записываем в основном Issue. При объединении ролей выбираем другого участника, не автора проверки. Формулы FM и смысл основного эксперимента должны уметь объяснить все.

## Проверяемые утверждения и связь с GitHub-задачами

Здесь **Т** — математическое утверждение, **К** — проверка реализации или протокола, **Г** — экспериментальная гипотеза. Для Т нужен вывод и пояснение; для К — воспроизводимая проверка; для Г допустим как положительный, так и отрицательный результат. Таблица задаёт требования к проверкам, а не их текущий статус: фактические результаты смотрим в связанных Issues/PR.

| ID / тип | Что проверяем | Как проверяем и что сохраняем | Задача |
|---|---|---|---|
| Т1 | В FM коэффициент взаимодействия пары равен ⟨vᵢ,vⱼ⟩: один вектор участвует во многих парах, поэтому коэффициенты связаны общими параметрами | Выписать три коэффициента с общим признаком i и показать, какие из них меняются при изменении vᵢ. Сохранить свою схему и формулу; не делать отсюда вывод о гарантированном выигрыше качества | [#2 — модель](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2), [#3 — объяснение](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) |
| Т2 / К1 | Прямой перебор пар и быстрое вычисление FM задают одну функцию | Вывести тождество ниже. На одних x и параметрах сравнить обе реализации, записать максимальную ошибку и допуск с учётом dtype; проверить несколько входов, включая разреженный | [#2](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2) |
| Т3 / К2 | При двух активных one-hot признаках user/item FM совпадает с MF с bias | Подставить признаки: ŷᵤᵢ = w₀ + bᵤ + bᵢ + ⟨pᵤ,qᵢ⟩. Сравнить предсказания при одинаковых параметрах. Не сравнивать два независимо обученных запуска как проверку тождества | [#2 — проверка](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2), [#3 — корректная интерпретация](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) |
| Т4 / К3 | При обнулении факторных векторов предсказание FM становится предсказанием bias-модели на user/item | Сравнить forward с одинаковыми линейными параметрами и V = 0. Это проверка вложенности моделей; для обучения FM использовать ненулевую случайную инициализацию V, иначе градиент взаимодействий при V = 0 равен нулю | [#2](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2) |
| К4 | Backpropagation даёт градиент выбранной функции потерь, а оптимизатор использует его для обновления параметров | На маленьком ненулевом примере проверить градиенты конечными разностями или независимым autograd, включая используемую регуляризацию. Для одного шага SGD сверить θ_new = θ_old − η∇L. Затем показать обучение на маленьком представимом примере; не требовать снижения validation RMSE на каждом шаге | [#2](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2) |
| К5 | Bias и FM сравниваются на одних наблюдениях без пересечения train/validation/test | Проверить ID строк и пересечения, словари по train, известность user/item в оценке. Сохранить seed, размеры до/после исключения неизвестных ID и долю сохранённых строк. Сверить список оцениваемых ID у моделей | [#1 — данные](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/1), [#3 — протокол](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) |
| К6 | RMSE и порядок сопоставления рейтингов с предсказаниями реализованы верно | Для y = [1, 3], ŷ = [2, 1] получить RMSE = √2.5 ≈ 1.5811; проверить совпадение ID строк, отсутствие NaN и общий расчёт метрики для моделей. Сохранить проверку | [#1](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/1), [#3](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) |
| Г1 — основная | Добавление факторизованных взаимодействий улучшает RMSE относительно bias на выбранном срезе MovieLens | Одинаковые данные/метрика, подбор настроек только по validation. Сохранить таблицу bias/FM и ΔRMSE = RMSE(FM) − RMSE(bias): отрицательное значение означает улучшение. Сначала согласовать сравнение и начать пилот; окончательный test — после выбора настроек, повторения по seed — до финала | [#2 — модели](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2), [#3 — эксперимент и вывод](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) |
| Г2 — дополнительная | Жанры могут улучшить качество FM относительно одних user/item | После готовности Г1 сравнить FM с жанрами/без них на одном split; фиксировать multi-hot кодирование. Чтобы отделить вклад новых линейных эффектов от взаимодействий, добавить baseline с линейными эффектами жанров. Улучшение не гарантировано | [#1 — признаки](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/1), [#2 — модель](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/2), [#3 — абляция](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/3) |
| Г3 — только при сохранении DCN | Cross-ветка может улучшить RMSE относительно небольшой DNN | Сравнить DNN/DCN на общем срезе при одинаковых embeddings и deep-ветке; сохранить настройки, параметры, время и метрики. Это необязательная гипотеза, не критерий готовности FM | [#4 — DCN](https://github.com/polushkin-ayu/ai360-recsys-2026/issues/4) |

Тождество для Т2 (сумма по f — по координатам факторных векторов):

```text
Σ_{i<j} ⟨v_i, v_j⟩ x_i x_j
= 1/2 · Σ_f [ (Σ_i v_if x_i)² − Σ_i v_if² x_i² ].
```

Квадраты справа сокращают самовзаимодействия при раскрытии скобок; это не добавление членов xᵢ² в модель.

## Как связать результат с задачей

В соответствующем Issue или PR указываем ID утверждения и доказательство проверки. Один PR может закрывать несколько пунктов, но чекбокс отмечаем только после предъявления результата. Для Г1–Г3 «проверено» не означает «получен выигрыш».

```text
Утверждение: К1 (прямой и быстрый forward)
Задача: #2
Статус: запланировано / в работе / проверено / заблокировано
Ответственный: <логин>
Проверяющий из другой команды: <логин>
Доказательство: <вывод/схема или commit + команда + конфигурация/seed>
Ожидаемый критерий: <равенство с допуском / отсутствие пересечений / сравнение метрик>
Фактический результат: <значения и ссылка на файл; заполнить после проверки>
Вывод и ограничения: <что установили и чего эта проверка не доказывает>
Следующий шаг: <действие и срок>
```

Для экспериментов дополнительно заполняем [журнал](experiment_log.md). Пример связи: К5 → #1 → сохранённые ID split и отчёт покрытия; К1 → #2 → проверка равенства; Г1 → #3 → таблица метрик на моделях из #2 и данных из #1.
