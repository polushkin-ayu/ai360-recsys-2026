# Обучение SVD++ на полном MovieLens 1M

Этот комплект добавляет самостоятельную SVD++ на PyTorch и отдельный эксперимент с подбором learning rate и регуляризации для каждого k. Он подготовлен по текущему `main` репозитория `polushkin-ayu/ai360-recsys-2026`, commit `da15862860d623f5dafdb92fa6ee28f447bae6bf`. Старые результаты, код других моделей и общий скрипт подготовки данных не перезаписываются. После завершения обучения новые результаты можно использовать для замены прежнего SVD++-раздела.

Полного поиска гиперпараметров в этом комплекте ещё нет: его нужно выполнить командами ниже. Проверены формула, градиенты, сохранение, возобновление, весь pipeline на синтетическом примере и техническое обучение на полном ML1M. Технические запуски не являются итоговыми результатами качества.

1. Используем существующее разделение данных.

Источник содержит 1 000 209 оценок, 6 040 пользователей и 3 706 фильмов с оценками. Скрипт репозитория делает общий случайный split 70/15/15 с seed 42. Мы не создаём новый split и не перенумеровываем ID.

| Часть | Исходных строк | Строк для RMSE |
|---|---:|---:|
| train | 700 146 | 700 146 |
| validation | 150 031 | 150 002 |
| test | 150 032 | 149 990 |

Из validation исключены 29 оценок неизвестных фильмов, из test — 42. Это общий протокол репозитория. В train-словаре 6 040 пользователей и 3 652 фильма; число 3 706 относится ко всему источнику.

TRAIN служит для градиентных обновлений и построения истории пользователя. VALIDATION служит для выбора лучшей эпохи, learning rate, регуляризации и k. TEST служит для итоговой оценки после фиксации всей серии. Во время подбора содержимое test.csv не разбирается: проверяются только контрольные суммы подготовленных файлов. Команда подготовки данных может читать test для проверки разделения; она не обучает модели и не вычисляет test RMSE.

В опубликованном отчёте split ID равен `44980861026c554d3b7d26ebd5bbf763ff0104d5629f40cc200ba2db38887663`. При воспроизведении на Linux получился `f8f6f4178788e3c718735b2e7f23e1918f8801df2a8778cceb8227bf5b031b62`: Windows записал вспомогательный selected_users.json с CRLF, Linux — с LF. Все остальные артефакты, включая все CSV с оценками и mappings, совпали побайтно. Код проверяет каждый CSV по опубликованному reference, проверяет содержимое JSON и сохраняет оба ID. Если изменились оценки, mappings или разделение, запуск будет отклонён.

2. Фиксируем формулу и смысл регуляризации.

Модель вычисляет

$$\widehat r_{ui}=\mu+b_u+b_i+q_i^\top\left(p_u+\frac{1}{\sqrt{|N_u|}}\sum_{j\in N_u}y_j\right).$$

Здесь N_u — множество уникальных фильмов пользователя только из TRAIN; в сумму входят факты взаимодействий, без умножения на рейтинг. При пустой истории сумма равна нулю. P, Q и Y — три независимые обучаемые таблицы. Mu фиксирована и равна среднему TRAIN; смещения пользователей и фильмов обучаются.

Это каноническая формула Surprise/Корена, самостоятельно написанная на PyTorch. Surprise не требуется. Это факторная модель, обучение которой идёт градиентным методом; вызова матричного SVD нет.

Минимизируем явно заданную функцию

$$J(\theta)=\frac{1}{N}\sum_{(u,i)\in TRAIN}(r_{ui}-\widehat r_{ui})^2+\frac{\lambda}{N}\left(\|b_u\|^2+\|b_i\|^2+\|P\|_F^2+\|Q\|_F^2+\|Y\|_F^2\right),$$

где N — число train-оценок, а нормы смещений означают суммы по всем пользователям/фильмам. Mu не регуляризуется. Используется Adam с weight_decay=0, без scheduler. Одно значение lambda управляет всеми пятью таблицами. AdamW weight decay и коэффициенты per-rating SGD из Surprise имеют другой смысл: переносить их численные значения сюда напрямую нельзя.

RMSE — корень среднего квадрата ошибки, без регуляризационного слагаемого. На графике сравниваем именно RMSE. Сравнивать penalized loss разных моделей с разными lambda некорректно для оценки качества предсказаний. В логах отдельно сохраняются train_mse и train_objective.

Предсказания не обрезаются до [1,5] ни в подборе, ни на графике. Это фиксированный протокол данной серии.

3. Одинаково обучаем каждый набор параметров.

Основная сетка:

| Параметр | Значения |
|---|---|
| k | 2, 3, 5, 10, 20, 30, 40, 50, 100, 150, 200 |
| learning rate | 0.001, 0.003, 0.01, 0.03 |
| lambda | 0.01, 0.1, 1, 10, 100 |
| seed для подбора | 11, 22, 33 |
| новые seed для итоговой серии | 101, 102, 103, 104, 105 |

Для каждой тройки (k, learning rate, lambda) модель запускается с нуля на каждом из трёх tuning seed. Для каждой отдельной модели сохраняется эпоха с минимальным validation RMSE. После 40 эпох без нового минимума обучение останавливается; максимум — 500 эпох. Берётся настоящий минимум, min_delta=0. В конце восстанавливаются все параметры лучшей эпохи.

Далее для каждого k выбирается пара (learning rate, lambda) с минимальным средним validation RMSE по трём seed. При точном совпадении среднего предпочтение определяется сначала меньшей lambda, затем меньшим learning rate. Настройки одного k не переносятся на другой.

После выбора параметров для каждого k модель заново обучается на пяти новых seed. Лучшая эпоха каждого такого запуска опять выбирается по validation. Эти пять моделей служат для итогового графика. k для основной модели фиксируется по среднему validation RMSE этой итоговой серии ДО просмотра test.

Стандартная сетка требует 11 × 4 × 5 × 3 = 660 запусков подбора и 11 × 5 = 55 итоговых обучений, всего 715. Расширение сетки добавляет запуски. Это конечный поиск по заданной области, а не доказательство глобально оптимальных гиперпараметров.

Используется одна и та же процедура инициализации: для факторов sigma = 0.1 / k^(1/4), смещения нулевые. При независимых начальных координатах это удерживает приблизительно постоянной дисперсию скалярного произведения k × sigma^4. Эта процедура заранее фиксирована для всей серии.

Чтобы не суммировать истории всех пользователей на каждом батче, TRAIN делится на группы по 128 пользователей; в группу входят все их train-оценки. За эпоху пользователи перемешиваются, каждая оценка используется ровно один раз, история каждого пользователя вычисляется один раз. Число рейтингов в группах различается, поэтому batch loss использует SSE × n_batches/N, а не обычный batch.mean(). В среднем по группам при фиксированных параметрах это даёт указанную полную функцию J. Это проверено сравнением градиентов.

Во время обучения сумма Y пересчитывается с актуальными параметрами и участвует в autograd. Во время оценки все профили вычисляются один раз под no_grad и используются для батчей предсказаний. Постоянного устаревшего кэша в обучении нет.

6. Проверяем скорость, затем запускаем полный подбор.

```bash
python -m src.svdpp_ml1m benchmark --k 2 200
mkdir -p results/svdpp-ml1m
python -m pip freeze > results/svdpp-ml1m/environment.txt
python -m src.svdpp_ml1m tune
```

Benchmark выполняет по три эпохи на полном TRAIN для маленького и большого k. Он записывается в benchmark.json и не участвует в выборе параметров. При проверке этого комплекта эпоха k=2 занимала примерно 0.5 с, k=200 — примерно 2.1 с. Это время на конкретном CPU; оно не предсказывает скорость вашего компьютера.

Для оценки бюджета использовать своё время эпохи, умноженное на число реально прошедших эпох и запусков. Например, при среднем времени эпохи 1 с и 150 эпохах 715 обучений требуют около 30 часов без учёта сохранения и загрузки. Early stopping может существенно менять бюджет. GPU также может помочь, но его скорость нужно измерить benchmark.

Каждый tuning run сохраняет JSON с параметрами, seed, метриками, лучшей эпохой и временем, а также CSV всей истории обучения. После завершения k появляются tuning_k{k}.csv и selected/k{k}.json. Test RMSE на этом этапе отсутствует.

Можно запускать k последовательно отдельными командами:

```bash
python -m src.svdpp_ml1m tune --k 2 3 5 10 20
python -m src.svdpp_ml1m tune --k 30 40 50 100 150 200
```

Не запускать несколько процессов одновременно в один output/checkpoint каталог: общие manifests рассчитаны на последовательное обновление. Параллельность потоков CPU управляется threads в конфиге и должна быть выбрана до первого tune.

Если процесс остановился, активировать то же окружение и повторить ту же tune-команду. Завершённые runs переиспользуются после проверки hashes. Текущий run возобновится с последнего атомарного checkpoint, сохраняемого каждые пять завершённых эпох; максимум четыре несохранённых эпохи пройдут повторно. Checkpoint включает текущую модель, Adam, порядок перемешивания, историю, счётчик early stopping и лучшие параметры.

7. Проверяем, достаточно ли поиска и обучения.

После подбора для всей сетки:

```bash
python -m src.svdpp_ml1m diagnose
```

До запуска fit поле missing_final_seeds будет заполнено — это ожидаемо. Посмотреть selection_diagnostics для каждого k и таблицы tuning_k{k}.csv.

Если лучший learning rate или lambda лежит на границе сетки, поиск следует расширить в эту сторону. Граничный оптимум сам по себе не доказывает ошибку, но означает, что область поиска ещё не окружила найденный минимум. Примеры расширения:

```bash
# Лучший lr=0.03: добавить 0.1 для соответствующего k.
python -m src.svdpp_ml1m tune --k 20 --extra-lrs 0.1
# Лучший lr=0.001: добавить 0.0003.
python -m src.svdpp_ml1m tune --k 20 --extra-lrs 0.0003
# Лучший lambda=100: добавить 1000.
python -m src.svdpp_ml1m tune --k 20 --extra-regs 1000
# Лучший lambda=0.01: добавить 0.001.
python -m src.svdpp_ml1m tune --k 20 --extra-regs 0.001
```

Новые значения добавляются к прежней сетке этого k. Проверяются все новые сочетания; прежние расчёты сохраняются. Все кандидаты получают те же три tuning seed. Повторная команда без --extra-* помнит уже расширенную сетку. Нельзя просто отредактировать существующий JSON с параметрами запуска: это изменит fingerprint и вызовет отказ смешивать разные протоколы.

Если selected_candidate_hit_epoch_cap присутствует, посмотреть кривые и лучшие эпохи в records/histories. Если validation ещё улучшается около максимума, увеличить max_epochs, например до 1000, в копии конфигурации, одновременно выбрать новые output_dir и checkpoint_dir и повторить серию с `--config configs/имя-копии.json`. У всех кандидатов должен быть один заранее выбранный достаточный бюджет и одинаковое правило early stopping. Не исправлять это просмотром test или увеличением числа эпох только у понравившегося на test k.

Низкий training loss при растущем validation RMSE означает переобучение; большую эпоху в таком случае выбирать не нужно. Провал качества при большом lr, осцилляции или nonfinite loss требуют проверки learning rate. Код отклоняет nonfinite loss/градиенты; упавший run не подменяется хорошим числом и не пропускается в поиске.

9. Фиксируем выбор, открываем test и строим графики.

Переходить к этим командам после проверки диагностики:

```bash
python -m src.svdpp_ml1m freeze
python -m src.svdpp_ml1m test
python -m src.svdpp_ml1m plot
```

freeze проверяет, что завершены все заранее определённые итоговые runs, сохраняет выбранные пары для каждого k и выбранный k по среднему validation RMSE. После freeze tune/fit для этой серии закрыты. Это не команда дополнительного обучения.

test оценивает ровно те 55 checkpoint, которые уже зафиксированы, на одинаковых строках test. В начале записывается отметка доступа к test. При прерывании test можно повторить; уже сохранённые test predictions проверяются и переиспользуются. По test нельзя выбирать learning rate, lambda, эпоху, seed или k и затем выдавать тот же test за независимую финальную оценку.

Мы сохраняем TRAIN=70% при итоговом обучении и не объединяем TRAIN с VALIDATION: так validation остаётся независимой для выбора эпохи, а истории и mu имеют одинаковый смысл во всей серии. Обучение на 85% после подбора возможно как отдельный протокол с фиксированным числом эпох, но его метрики и validation-кривые нельзя смешивать с этим исследованием RMSE(k).

График показывает среднее и выборочное стандартное отклонение RMSE по пяти final seed. Это разброс инициализации и порядка батчей при одном фиксированном split; это не доверительный интервал и не оценка разброса между разными splits. Точки размещаются по настоящим численным k, без полиномиальной аппроксимации или подгонки формы кривой.

Test-кривую по всем заранее объявленным k можно показывать как описание финальной серии. Основной k при этом остаётся выбранным по validation. Поиск гиперпараметров на validation тоже даёт некоторый оптимизм validation-метрики; независимый test оценивает зафиксированную процедуру.

Даже после правильного подбора RMSE(k) не обязан быть U-образным. Он может снижаться, выходить на плато или слегка колебаться. Увеличение k не ухудшает выразительную способность модели, но качество на новых данных зависит от регуляризации, конечного обучения, случайности и самого split. Форма графика не служит критерием корректности реализации.
