# Как читать код SVD++

Начните с `src/model.py`, затем прочитайте `src/training.py`, после этого `train.py`.
Графики находятся в `src/plotting.py`: итоговые RMSE от k на validation/test,
train loss по эпохам и диагностика подбора гиперпараметров.
В `src/experiment.py` графики вызываются автоматически после этапов tune и fit.

## 1. Истории: Histories

Из train берутся пары `user_idx`, `item_idx`. Повторы удаляются, пары сортируются.
`items` — объединённый список фильмов всех пользователей; `offsets` — границы
каждого пользователя в этом списке; `lengths` — размеры историй.
Такое представление называется CSR и позволяет хранить истории разной длины.
Например, истории `[0, 2]`, `[1]`, `[]` дают `items=[0,2,1]`,
`offsets=[0,2,3,3]`, `lengths=[2,1,0]`.

`select()` выбирает только истории нужных пользователей. Оценок в нём нет:
для неявной части модели важен факт наличия фильма в train-истории.

## 2. Параметры: SVDPlusPlus.__init__

`nn.Embedding(a, b)` — обучаемая таблица из `a` строк длины `b`.
По индексу пользователя или фильма она возвращает нужную строку.

| Параметр | Размер | Значение |
|---|---|---|
| `bu` | число пользователей × 1 | Сдвиг среднего рейтинга пользователя |
| `bi` | число фильмов × 1 | Сдвиг среднего рейтинга фильма |
| `p` | число пользователей × k | Явный эмбеддинг пользователя |
| `q` | число фильмов × k | Эмбеддинг фильма, для которого делаем прогноз |
| `y` | число фильмов × k | Вклад фильма из истории в профиль пользователя |
| `mu` | скаляр | Средняя оценка по train, фиксирована |

Сдвиги начинают с нуля. `p`, `q`, `y` начинают со случайных значений нормального
распределения; затем Adam обучает их по оценкам train.
Стандартное отклонение `0.1 / k**0.25` сохраняет сравнимый масштаб начального
скалярного произведения при разных `k`.

## 3. Прогноз: profiles → forward → from_profiles

`profiles()` суммирует `y_j` для всех фильмов истории с помощью
`F.embedding_bag(..., mode="sum")`, делит сумму на корень из длины истории
и прибавляет `p_u`. Для пустой истории неявный вклад равен нулю.

`forward()` выделяет уникальных пользователей batch, чтобы не считать одну
историю заново для каждой оценки. `from_profiles()` добавляет `mu`, `bu`, `bi`
и скалярное произведение профиля с `q_i`.

Градиент через `embedding_bag` попадает в `y`, поэтому таблица неявных факторов
также обучается. Во время обучения вычисления строятся заново в каждом forward.

## 4. Обучение: fit_one

Последовательность одной эпохи:

1. Перемешать активных пользователей.
2. Взять следующие `batch_users` пользователей и все их оценки из train.
3. Обнулить старые градиенты: `optimizer.zero_grad()`.
4. Получить прогнозы: `model(users, items)`.
5. Посчитать квадрат ошибки плюс L2 с нормировкой полного опыта.
6. `loss.backward()` вычисляет производные по `bu`, `bi`, `p`, `q`, `y`.
7. `optimizer.step()` обновляет параметры Adam.
8. После всех batch пересчитать train/validation RMSE при одних текущих параметрах.
9. Если validation RMSE улучшился, сохранить лучшую модель; иначе увеличить счётчик ожидания.
10. Сохранить checkpoint для продолжения. Остановиться при patience или лимите эпох.

Функция возвращает модель лучшей validation-эпохи, её метрики и всю историю.
`last.pt` и `model.pt` могут содержать разные веса: первый нужен для продолжения,
второй — для использования лучшей модели.

Test не нужен для этих шагов. В полном эксперименте он открывается после
подбора, финальных повторов и `freeze`.

## 5. Проверка метрик и двухэтапный подбор

`FixedOrderScorer` в `src/training.py` один раз проверяет ID и сохраняет
неизменные копии ID/целевых оценок. Внутренний `predict()` возвращает прогнозы
в порядке входных строк. В каждой эпохе проверяются форма и конечность прогнозов,
но уникальность неизменных ID повторно не вычисляется. Для внешних прогнозов
сохраняется строгий `score()`; scorer также принимает явные ID для проверки порядка.

`tune()` в `src/experiment.py` сначала сравнивает все пары на первом tuning seed
на полном предварительном бюджете. `shortlist_candidates()` оставляет лучшие
lambda отдельно для каждого learning rate. Затем пары подтверждаются на всех
трёх tuning seeds. Окончательное решение использует средний validation RMSE.

`min_epochs` запрещает раннюю остановку до предварительного бюджета — и при
первом сравнении, и при подтверждении. Первый seed подтверждения продолжает
последнее состояние предварительного этапа; checkpoint хранит текущие веса,
Adam, RNG, историю, лучшую модель и счётчик эпох без улучшения. При повторном
прерывании активный checkpoint подтверждения имеет приоритет над предварительным.
Подписи протокола и контрольные суммы проверяются до продолжения.

`screening_k<k>.csv` содержит метрики одного seed, `shortlists/k<k>.json` — список
оставленных пар, `tuning_k<k>.csv` — средние/SD подтверждений. Отдельные heatmap
показывают разные бюджеты. Подпись списка кандидатов входит в окончательный выбор;
расширение сетки делает прежний выбор незавершённым до нового `tune`.
Весь отбор работает с train и validation, без test.
